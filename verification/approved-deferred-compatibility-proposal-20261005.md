It adds one author-owned field to existing failureTests/regressions contracts and uses only existing operations, references, executor routes and truth/evidence vocabularies. It does not adopt the historical three-operation amendment or require a new universal independent reviewer.

## Proposed addition to Section32.4A and FIELD_REGISTRY

A definition whose EXECUTION_TEST_ID supplies a deferred execution route must contain the agent-owned field EXECUTION_COMPATIBILITY. Missing, FALSE, UNKNOWN, malformed, stale or insufficiently supported compatibility blocks canonical definition admission. A definition with a future schedule that requires EXECUTION_TEST_ID cannot evade this condition by omitting that required relationship. Ordinary legacy owning-stage definitions with no deferred test relationship retain their existing contract and execution path.

| FIELD_REGISTRY family | Field | Owner | Type | Requiredness | Normalizer |
|---|---|---|---|---|---|
| failureTests (Stage07) | EXECUTION_COMPATIBILITY | AGENT | OBJECT, closed nested contract below | Required for a deferred definition written by an already authorized owning operation, including Stage07 COMPLETE and the existing owning Stage07 EXECUTE_FAILURE_TEST writer; retained legacy immediate definitions are exempt as above | deferred-definition-compatibility/1 |
| regressions (Stage15) | EXECUTION_COMPATIBILITY | AGENT | OBJECT, closed nested contract below | Required for a deferred definition written by an already authorized operation, including Stage15 COMPLETE, the existing owning Stage15 EXECUTE_REGRESSION writer, and Stage17 REGRESSION; the same contract follows its canonical family at either stage | deferred-definition-compatibility/1 |

This amendment preserves every operation's existing writer permissions. Ordinary owning-stage Stage07 EXECUTE_FAILURE_TEST and Stage15 EXECUTE_REGRESSION currently have definition-writing permissions; when an already authorized response writes a deferred definition, the same required compatibility field applies. The field is not supplied on execution receipts. Later-than-owner conditional execution operations remain receipt-only and cannot rewrite definitions. Stage17 ROOT_CAUSE/CORRECT do not gain regression-author privileges. Application-owned EXECUTION_TEST_ID, IDs, hashes, scope, timing consequences, evidence normalization, receipts and gates remain application-owned. No new operation, family, executor or application store is authorized.

The common required object properties are exactly:

| Property | Type and accepted syntax | Meaning |
|---|---|---|
| actualTargetCompatibility | STRING, exactly TRUE/FALSE/UNKNOWN | Author's supported semantic determination that the execution test addresses the actual target contract of this definition. |
| outcomeCompatibility | STRING, exactly TRUE/FALSE/UNKNOWN | Author's supported semantic determination that the reviewed observation meaning establishes the definition's required rejection or PRE/POST outcomes. |
| actualTarget | Nonempty STRING | Exact described subject, preserved fixture and required tested inputs, using supplied current identities where available and the published phase/input contract for legitimately future targets. It cannot fabricate a future artifact/run/candidate or replace a typed relationship. |
| rationale | Nonempty STRING | Material reasoning for target and outcome correspondence, including limitations; it does not itself prove bytes, execution, provenance or independence. |

A failureTests object additionally requires exactly expectedRejectionMeaning: nonempty STRING explaining how the reviewed actual observation establishes the existing EXPECTED_REJECTION for the bound known-invalid fixture.

A regressions object additionally requires exactly preCorrectionFailureMeaning and postCorrectionSuccessMeaning, both nonempty STRINGs explaining how the same reviewed test/predicate and preserved negative fixture establish the original failure on the defective target and success on a distinct corrected target. These meanings correspond to existing PRE_CORRECTION/VIOLATED and POST_CORRECTION/SATISFIED receipt semantics. They are expected meanings, never a claim those executions occurred.

No other properties are permitted. Missing differs from null; null is prohibited. Strings obey the owning stage's existing text/resource limits; this contract does not shrink supported workloads or create an extra unbounded input channel. The existing wrapper evidenceRefs supplies its exact supporting evidence, resolved by normal typed/current/authorized reference rules; nonempty IDs alone are insufficient.

## Application acceptance and normalization

The following steps are one shared authority, consumed at proposal preparation, projected-canonical integrity, operator commit/freshness recheck, execution planning, due-stage gates and restoration. Passing admission remains separate from stage completion or release.

1. Check the closed representation, explicit TRUE for both determinations, current typed EXECUTION_TEST_ID, same governing requirement, applicable current scope, compatible phase/timing, and current accepted independent review of that exact test semantic hash. TRUE is necessary and never sufficient by itself. No keyword search or equality of arbitrary prose derives a favorable determination.
2. Bind the proposed definition's complete canonical meaning (fixture, reproduction/detection, correction, timing, resolved references and EXECUTION_COMPATIBILITY) and supporting evidence to the exact current reviewed test/input/observation contract, current authorized scope, author reservation and raw response. Use application-calculated IDs/hashes and existing proposal/reservation/context/raw evidence records; the actor copies published identities and never allocates replacements. Recheck those material inputs immediately before commit. A changed test, definition, evidence, scope or history activation invalidates the prior authority and uses the existing fresh reservation/correction/confirmation route.
3. Check actual preservation of the fixture and attributable support that it represents the recorded defect/known-invalid case. Required byte-backed fixtures must resolve to actual app-verified stored bytes; filename/hash declarations are insufficient. A supported inline literal or isolated canonical-state fixture uses its exact lossless value/identity and the appropriate recorded provenance. The definition's existing defect/requirement relationships and evidence must actually address that fixture; an unrelated successful ordinary observation cannot prove negative execution or compatibility.
4. For a native route, mechanical compatibility may be established only for what the existing reviewed Test IR, explicit literal/predicate, EXECUTABLE_INPUT_BINDINGS and published target/fixture selectors actually determine. The application must resolve the exact preserved fixture, required target input contract, primitive/argument types and expected observation meaning. It must not execute not-yet-due work, interpret fixtureMeaning/rationale strings as selectors, or assert an arbitrary semantic proposition from a hash. If existing native syntax cannot mechanically express the semantic correspondence, that mechanical assessment is UNKNOWN. A complete supported author semantic compatibility determination may establish the correspondence at its honest recorded basis while the valid reviewed native Test IR remains the executor. Compatibility assessment basis and execution mode are separate; do not force a valid native executor to become external merely because its meaning needs supported author interpretation. If neither mechanical nor qualified author-supported compatibility is established, retain a blocker.
5. For a supported external route, the author may provide an attributable semantic compatibility determination under ordinary agent authority. Support must include the current reviewed test's actual input/artifact/observation contract, the preserved fixture/defect evidence, and the reasoned target/outcome correspondence. It may use the existing ARTIFACT_REQUIREMENTS/handoff and permitted current context; external inputs are not forced into the native EXECUTABLE_INPUT_BINDINGS grammar. A legitimately future target is identified by its allowed reviewed phase/input contract rather than nonexistent future bytes/identities. Author-supported semantic qualification is the conjunction of all of the following: (a) the author operation is permitted and its actual raw response, context and reservation are bound to the current proposed definition and scope; (b) EXECUTION_TEST_ID resolves to exactly the current independently reviewed test semantic hash and its actual input/observation contract; (c) preserved negative fixture and applicable recorded defect/known-invalid-case evidence are bound to this definition, with actual verified custody wherever bytes are required; (d) both controlled determinations are TRUE and all family-specific target/outcome meanings and rationale are complete; (e) every required support reference resolves by family, current identity, authorized scope and recorded provenance and has sufficient support for its declared proposition under the existing evidence rules; and (f) no existing controlled contradiction or unresolved mandatory-support state remains. Failure of any term leaves compatibility FALSE or UNKNOWN, as appropriate, and blocks admission. This conjunction qualifies the supported author's semantic judgment as EXTERNALLY_SUPPORTED where that basis is established; the machine validates the binding and qualification facts and does not claim to prove arbitrary-prose semantic truth. A bare label, generic evidence, populated IDs, or nonblank text cannot satisfy it. The same attributable semantic qualification may support a native test's meaning without changing its executor. No qualification promotes an author claim to application-observed or verified semantic inference.
6. Missing required fixture/support, declared FALSE/UNKNOWN, a known contradiction, a wrong/stale/unauthorized reference, or current evidence whose existing authority/sufficiency state is unknown/insufficient prevents a commit-ready canonical definition. Return a precise typed validation reason and the existing recovery route, retain complete raw bytes and recoverable work, and distinguish changed state/storage failure from a contract error. No favorable fallback, implicit migration or silent default is allowed.
7. Preserve the raw compatibility object and supporting CONTENT. Any normalized result retains its actual epistemic basis: application-established mechanical facts are distinguished from AGENT_SEMANTIC_OBSERVATION/EXTERNAL_CLAIM and appropriately supported external interpretation under the existing evidence model. A declaration does not establish human action, byte custody, actual execution, future success, provider independence, release authority or SATISFIED receipt. The application may mark definition admission compatible only after all required checks/support pass; actual execution evidence remains separately due and must use distinct PRE/POST executions/input identities.

An accepted review of an earlier test alone is insufficient to establish the later arbitrary fixture/target/outcome pair. The evidence-support check must not be reduced to populated IDs, nonblank reasoning, a selected profile index or a generic successful observation. External semantic authority remains a supported claim with its recorded basis, not stronger authentication or universal machine verification. A report or current recorded authority that expressly leaves target/outcome compatibility UNKNOWN cannot be normalized to TRUE.

Current unknown legacy deferred definitions remain retained with their identities, raw bytes, historical versions and evidence. They cannot satisfy current deferred work until the existing versioned correction/confirmation route supplies the missing current contract/support. This does not rewrite historical data, retire the obligation or bypass future execution. Future valid definitions remain registered, visible and unexecuted; validation of their admitted compatibility occurs before the planner's FUTURE scheduling branch.
