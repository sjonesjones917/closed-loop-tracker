DECISION RULE
§0 authorizes implementing and preserving compliant mechanisms and forbids making the user construct schemas. It does not override explicit closure. §14.5 requires complete field contracts, rejects undeclared defaults, and expressly makes a field contract not explicitly specified or uniquely derivable under its closed rules an UNDEFINED_FIELD_CONTRACT requiring specification change. Its corresponding operation closure is equally explicit. §34.3 requires release-bearing derivation/normalizer semantics to come from the source or an explicitly named versioned normative algorithm.
An owner assignment is not unrestricted permission to invent gate-bearing semantics. Conversely, encoding an already defined predicate, choosing an expressly delegated resource limit, or selecting an implementation technique that preserves all defined outcomes is not a source amendment.

1. humanInputRequests — REQUIRED_AMENDMENT, narrowly for closed item/value/default contract
Already defined: §17.1 requires this response member; §18 makes it the final structured fallback, gives the eight controls, rejects unknown keys, reserves actual answers to SAVE_HUMAN_INPUT, and specifies invalidation/replacement consequences. Human versus agent authority is already controlled by §§14.2–14.4.
Missing: the closed accepted item-key set and the requiredness/nullability/cardinality/default rules are not uniquely supplied by these sections or §14.5's defaults. A declaration that unknown keys are rejected does not identify which keys are known. The proposed temporaryKey/question/whyRequired/affectedStageFields/affectedRecords/answerType/allowedValues object and optional blocking property are one possible contract, not an already mandated one.
Concrete semantic impact: which otherwise meaningful requests are rejected, which answers are admissible, how requests bind affected records, and especially whether omitted blocking automatically means true. That default directly affects readiness and is specifically the sort of undeclared default §14.5 prohibits.
No human schema work needed: the team supplies the exact narrow contract and example accepted/rejected messages. Existing control names and SAVE_HUMAN_INPUT rules need no reapproval. Current workflow-schema.js RESPONSE_VALUE_CONTRACTS and temporary-key grammar show the chosen implementation, not authority for adopting those defaults.

2. TARGET_AVAILABILITY_CONDITION — REQUIRED_AMENDMENT for the proposed additional closed grammar; due/evidence logic ALREADY_DEFINED
Already defined: §16.1 states the DUE_NOW conjunction and when UNKNOWN availability blocks; §21.17 binds timing to test role/proof obligation; §29.11 preserves future obligations; §§29.12–29.13 supply supported truth states, missing-data behavior, the closed proof language and its truth tables. §§19/35 and family/current-scope rules already establish actual bytes and identity requirements. These are not missing timing policy.
Missing: the source does not define TARGET_AVAILABILITY_CONDITION as the supplement's new PHASE_TARGET/CURRENT_RECORD/VERIFIED_ARTIFACT_BYTES/ALL_OF/ANY_OF/AT_LEAST_K object language, its property contracts, or its exact reference-to-target mapping. Merely borrowing the §29.13 truth tables does not define new atomic leaf semantics or establish that these new node types belong to that closed language. The pinned schema selects OBJECT and publishes a particular condition validator; this alone is not source authority.
Concrete semantic impact: whether a target is considered present, absent or unknown; whether mere record existence suffices; and therefore whether an otherwise required obligation blocks now or is deferred. The proposed distinction between known absence and unestablished identity must preserve §29.12's rule that missing data is UNKNOWN unless a closed universe proves FALSE.
Narrowing route: an exact lossless reference to an existing accepted proof contract, evaluated solely through already defined proof/currentness/byte rules, would not require inventing a second condition language. If the integrator demonstrates that representation and every §14.5 property are uniquely derivable, the predicate evaluation becomes ALREADY_DEFINED. This review found no such source derivation for the proposed six-variant grammar. Do not tell the user that choosing due stages or truth tables is their job.

3. closed-loop-raw-units/1 — REQUIRED_AMENDMENT for deterministic unit boundaries/accounting algorithm
Already defined: §6.5A requires deterministic media-specific unitization, stable identities and source locations, treatment of comments/annotations/tracked changes/metadata/embedded or inaccessible content, supported subdivisions, and fixed challenge thresholds. §34.2 already governs canonical IDs; §21.12 permits unsupported adapters to route externally.
Missing: exact structural boundaries/order/deduplication when deriving units, including treatment of empty or whitespace-only lines and distinct supplied occurrences. Naming closed-loop-raw-units/1 identifies the needed normative algorithm but does not itself spell out that algorithm.
Concrete semantic impact: splitting one text into lines rather than sections changes the unit universe, completeness denominator and 500-unit challenge trigger; omission of comments or duplicate occurrences can hide unexamined material. These are release-bearing intake semantics, not cosmetic serialization.
The proposed physical-line rules are a candidate policy, not uniquely mandated. They need independent coverage tests and review against preservation of unsupported/inaccessible subdivisions. Adapter implementation mechanics, code organization and existing canonical ID allocation do not require human approval.

4. Test IR authoring/primitive/parser/selector/regex/numeric/error contract — REQUIRED_AMENDMENT only for remaining result-bearing semantics, not the whole runtime descriptor
Already defined: §§21.1–21.17 define application-owned IR; explicit acyclic dataflow; primitive inventory; prohibitions; selector minimum and excluded syntax; CSV's explicit parameter binding; UTF-8; regex minimum/exclusions; exact integer and precision rules; immutable input bindings; external routing; resource-limit delegation; terminal dispositions; and semantic version/invalidation requirements. The Stage 06 contract requires publishing the actual registered operations and arguments. Most of this supplement repeats or instantiates those duties.
Express implementation selections: §21.14 explicitly delegates limit constants. §21.2 permits authoring shortcuts compiling to identical canonical IR. §21.10 expressly permits exact decimal-string interpretation and external routing for unsupported precision. Safe parser implementation, equivalent diagnostic wording, registry generation and mathematically equivalent algorithms do not each need source amendments.
Actual remaining semantic gaps: the proposed published runtime says COUNT of text means UTF-16 code units; no-match JSON selection becomes UNDETERMINED while some XML suffix cases return an empty array; UNIQUE uses canonical-JSON equality and preserves first occurrence; SORT has a default domain/direction; and PARSE_JSON accepts only certain numeric spellings. These are not all determined by the mere primitive names. Where a choice changes accepted input, a normalized canonical result, or SATISFIED/VIOLATED/UNDETERMINED behavior, §§14.5/34.3/21.16 require source-grounded closed semantics rather than taking existing code as its own authority.
Concrete impact example: COUNT on a string containing a supplementary Unicode character differs between code-unit and code-point semantics and can reverse ASSERT_EQ. A missing selector path interpreted as [] versus an unknown execution result can reverse a zero-count assertion. These are intelligible product consequences; “approve our 45 KB runtime object” is not an adequate explanation.
Do not adopt every current detail automatically. Resolve only uncovered observable semantics, retain requirements already fixed by the source, prove compatibility or invalidate affected tests/results, and do not treat version/digest pinning as semantic approval.

5. Expected variance representation/freezing/evaluation — REQUIRED_AMENDMENT for closed normalized representation; semantic outcome/ownership largely ALREADY_DEFINED
Already defined: §38.1 assigns AGENT proposed dimensions/rationale and APPLICATION identity, normalized contract, frozen timing, scope, hash and evaluation use. Stage 06 requires complete variance contracts; Stage 13 compares all ten runs against frozen contracts, records allowed variance, defects prohibited variance and blocks UNKNOWN; Stages 18/19 preserve the convergence consequences. §§26.5 and 29.15 already govern independent materiality review and unreconciled uncertainty. §31 supplies metrics without new release thresholds.
Missing: a unique closed contract for normalized inputs/outputs, required fields, normalization mappings and any accepted defaults. The supplement's DIMENSIONS/ALLOWED_VARIANCE/RATIONALE mapping, embedded versus direct forms, extension handling and receipt contracts are a chosen representation, not uniquely stated by §38.1. The exact normalizer is release-bearing because its bytes/hash bind the frozen contract.
Concrete impact: whether two differently represented authored contracts count as the same frozen agreement, what is excluded/preserved in its hash, whether a missing rationale or additional property is rejected, and whether changed meaning makes proof stale. Those differences cannot be laundered through a code-generated descriptor.
Do not escalate project-specific allowable variance as a universal human decision: the source explicitly delegates substantive semantic proposal/review to the relevant agents. Nor is the exact internal moment of creating a frozen proposal automatically a policy choice: a validation-time immutable snapshot is permissible only if it is never misrepresented as semantic approval or used before required acceptance/review. The proposed independent review modes primarily restate existing obligations and need correctness review, not blanket new human responsibilities.
The current greatest-count/denominator diagnostic agreement calculation should be checked against §31 and the existing nine-of-ten case; it must never make unanimous failure acceptable. This review does not accept an extra release threshold.

6. Minimum external input-binding basis — REQUIRED_AMENDMENT for the missing per-operation minimum assignment
Already defined: §26.6 names the available basis values; echoes establish at most EXTERNALLY_SUPPORTED; SELF_ASSERTED/UNKNOWN cannot satisfy byte-exact possession contracts. §§24–25 define exact package/member bindings, and §§26.4–26.6 preserve independence limits. Those rules do not equate external identity echoes with application-observed possession.
Missing: which minimum applies to each external operation. The source says every operation contract declares a minimum, but does not uniquely assign EXTERNALLY_SUPPORTED to every external-agent operation or specify a general default selecting the weakest nonprohibited basis. §14.5's operation closure prevents treating this open assignment as arbitrary implementation policy.
Concrete semantic impact: a run may be admitted on attributable echoed package/member identities under EXTERNALLY_SUPPORTED while a VERIFIED_EXTERNAL minimum requires an accepted attestation contract and could block that same run. The supplement's universal minimum is an admissibility policy, not just a schema enum.
Narrow resolution: publish the exact operation/minimum mapping and preserve stronger evidence requirements of particular accepted proof obligations and independence dimensions. Do not invent a requirement for universally verified possession from the file-first architecture; conversely, do not infer that the weakest allowable enum is automatically the mandated minimum. Pinned workflow-schema.js hard-codes EXTERNALLY_SUPPORTED for all external operations, proving only the implementation selection.

7. Repository physical-acceptance challenge expiry — IMPLEMENTATION_CHOICE; validity/rejection rules ALREADY_DEFINED
§45.2 empowers CI or the authorized acceptance controller to issue an unpredictable challenge bound to the exact build, origin, target, procedure and test project, and requires rejection of reused, mismatched, unknown or expired evidence. It does not specify a universal challenge lifetime, nor require the product specification to contain a minimum/maximum duration. §§17.11/29.14 already constrain real-time evidence bases and UNKNOWN freshness.
The controller can select and freeze a bounded lifetime for an actual acceptance procedure, record issue/expiry and its accepted clock basis, then enforce the frozen interval and single use. That is execution/acceptance management delegated to Dot under M00, not a new runtime producer or schema selection imposed on a project user.
The proposed 60–86,400-second range and default 3,600 seconds are additional restrictions, not an identified missing source obligation. Current generate-mobile-acceptance-target.mjs uses this implementation choice; preserving a compliant documented value is allowed under §0. The controller should choose a practical window for the actual physical procedure and regenerate an expired challenge. It must not extend an already expired challenge in place, use device time as trusted authority, or relabel stale/mismatched evidence.
No human normative amendment has been demonstrated necessary for selecting that duration. A proposal to accept expired evidence, waive the challenge, accept the wrong build or change required physical-device proof WOULD change the controlling acceptance requirement and is outside this implementation choice.
