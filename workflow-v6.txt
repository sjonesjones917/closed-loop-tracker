Closed-Loop Agent Reliability Workflow

1. Initialize the job
Create a job record before doing any substantive work.
Record:
• JOB_ID
• exact user objective;
• exact deliverable requested;
• all supplied files, messages, links, data, and constraints;
• required output format;
• deadline or temporal scope, if any;
• known authoritative sources;
• available tools;
• prohibited actions;
• unknown information that may affect correctness.
Do not rewrite the user’s objective into a different objective.
Separate explicit user requirements from assumptions.
If a required fact is unknown, record it as UNKNOWN. Do not fill it with an inferred value unless inference is expressly permitted.
Assign a version identifier to the complete input set.

2. Build the source inventory
Identify every source that may govern correctness.
For each source, record:
• source identifier;
• title or description;
• source type;
• origin;
• version;
• publication or effective date when relevant;
• authority level;
• whether it is mandatory, informative, or evidentiary;
• which portions are relevant;
• whether it conflicts with another source.
When current external facts affect correctness, research them using authoritative and current sources.
When the task depends on supplied files, inspect the actual supplied files rather than relying on filenames, summaries, or prior descriptions.
When multiple sources conflict, determine which source controls by applying the appropriate authority hierarchy for the task.
Do not silently choose between unresolved authoritative conflicts.
Record unresolved conflicts as blockers.

3. Research the requirements
For each source in the inventory:
1. Read the portions capable of imposing, limiting, or defining the requested result.
2. Extract every statement that changes what the final product must contain, omit, preserve, calculate, demonstrate, or accomplish.
3. Separate mandatory requirements from recommendations, examples, explanatory text, and optional practices.
4. Identify requirements created directly by the user’s request even when no external authority states them.
5. Identify requirements created by the intended output format or technical medium.
6. Identify requirements created by dependencies between parts of the deliverable.
7. Identify factual propositions that must be true for a requirement to apply.
8. Identify edge conditions and exceptions.
9. Record exact source evidence for each externally derived requirement.
10. Search specifically for requirements that could invalidate, contradict, or restrict requirements already found.
Continue research until another research pass produces no new material requirement category and every known controlling source has been examined.
Do not stop because the initial obvious requirements have been found.

4. Compile the requirement specification
Create one atomic requirement record for every independently testable obligation.
Use this structure:
REQ_ID:
REQUIREMENT:
TYPE:
SOURCE:
SOURCE_LOCATION:
AUTHORITY:
APPLICABILITY:
DEPENDENCIES:
PROHIBITIONS:
VERIFICATION_METHOD:
EXPECTED_EVIDENCE:
FAILURE_CONDITION:
STATUS:
Write requirements so that two independent evaluators applying the same evidence should reach the same result.
Split compound requirements.
Bad:
REQ-014:
Make the document accurate, complete, professional, and properly formatted.
Correct:
REQ-014:
Every factual statement derived from Source A must agree with Source A.
REQ-015:
Every section required by the governing format must be present.
REQ-016:
The document must contain no unresolved internal contradiction.
REQ-017:
Page margins must satisfy the specified dimensional requirement.
For every qualitative requirement, define what observable condition establishes satisfaction.
Do not use undefined criteria such as:
• good;
• strong;
• professional;
• complete;
• correct;
• sufficient;
• appropriate;
• perfect.
Replace each with measurable conditions.

5. Resolve the requirement set
Check the complete requirement set for:
• duplicate requirements;
• conflicting requirements;
• requirements that cannot simultaneously be satisfied;
• undefined terms;
• circular dependencies;
• missing prerequisites;
• unsupported requirements;
• requirements whose applicability cannot be determined;
• requirements with no possible verification method.
Resolve every resolvable defect.
If a mandatory requirement cannot be resolved because required authority or evidence is unavailable, mark the affected work BLOCKED.
Do not proceed as though the requirement were satisfied.

6. Build the verification suite before writing the production instruction
Create at least one verification procedure for every mandatory requirement.
Use:
TEST_ID:
REQ_ID:
TEST_TYPE:
INPUTS_REQUIRED:
PROCEDURE:
EXPECTED_RESULT:
FAILURE_CONDITION:
EVIDENCE_PRODUCED:
Choose the strongest available verification method in this order:
1. formal proof or exact computation;
2. deterministic programmatic test;
3. schema or structural validation;
4. exact source comparison;
5. rule-based evaluation;
6. independent semantic evaluation;
7. expert or authorized human judgment when the task requires it.
Do not use an AI evaluator for a property that can be deterministically checked.
Create separate tests for separate requirements.
Confirm that every mandatory requirement is covered.
Calculate:
mandatory_test_coverage =
mandatory_requirements_with_tests /
total_mandatory_requirements
Do not proceed until:
mandatory_test_coverage = 1.00
unless a requirement is explicitly blocked and the workflow is stopping on that blocker.

7. Build failure tests
For every requirement, determine at least one way the requirement could be violated.
Construct malformed, incomplete, contradictory, stale, incorrect, or adversarial cases where applicable.
Examples include:
• delete a required input;
• substitute a wrong version;
• alter a required number;
• duplicate an identifier;
• introduce a contradiction;
• remove a required section;
• add prohibited material;
• corrupt a cross-reference;
• provide a malformed file;
• inject instructions inside source material;
• provide two conflicting authorities;
• make a tool unavailable;
• provide an unsupported factual assertion.
For each test, define the required system response.
The system must detect the defect, reject the affected result, or block the affected operation.
A validator that accepts a deliberately constructed invalid case is defective.
Correct the validator before continuing.

8. Author the production instruction
Write the instruction from the compiled requirements, not directly from memory of the original request.
The instruction must explicitly specify:
Objective
State exactly what artifact or result the execution agent must produce.
Inputs
Identify what material the agent may use.
Specify how conflicting, missing, or malformed inputs must be handled.
Source authority
Specify which source controls when information conflicts.
Scope
Specify what the agent must do and what it must not do.
Defined terms
Define every specialized term whose interpretation could materially change the result.
Required procedure
Describe the actual operations the agent must perform and their required order.
Do not write:
Research all requirements.
Write the method:
Inspect each identified governing source individually. Extract each statement that imposes an obligation, restriction, exception, required element, prohibited element, numerical condition, structural condition, or procedural condition. Record each extracted requirement with its exact source location. Perform a second pass specifically searching for exceptions, conflicts, and requirements omitted during the first pass.
Do not write:
Verify the result.
Write:
Evaluate every mandatory requirement individually. Run its assigned deterministic test when one exists. For requirements requiring semantic evaluation, compare the candidate result directly against the requirement and its source evidence. Record the evidence supporting the determination. Reject the candidate if any mandatory requirement is violated or cannot be established.
Decision rules
For every material branch, define what condition selects each path.
Tool rules
Specify which operations require which tools and what to do if a required tool fails.
Output contract
Specify exact required artifacts, sections, fields, formats, naming conventions, and relationships.
Failure handling
Require:
TRUE → requirement established
FALSE → requirement violated
UNKNOWN → requirement not established
Never permit UNKNOWN to be silently converted to TRUE.
Completion criteria
Define the exact conditions under which execution may terminate successfully.

9. Preflight the production instruction
Use a separate evaluation process to inspect the instruction without executing the target work.
Examine every sentence.
For each sentence ask:
1. Can it be interpreted in more than one materially different way?
2. Does it reference an undefined object?
3. Does it depend on information not supplied?
4. Does it conflict with another instruction?
5. Does it require an unavailable capability?
6. Can compliance with it be objectively verified?
7. Is the responsible operation clear?
8. Is its ordering relative to dependent operations clear?
9. Does it specify what happens on failure?
10. Does it trace to a requirement or necessary execution control?
Correct every material defect.
Repeat preflight until no known material instruction defect remains.
Version the result:
INSTRUCTION-v001

10. Freeze the test candidate
Freeze together:
INPUT-vN
SOURCE-SET-vN
REQUIREMENTS-vN
TEST-SUITE-vN
INSTRUCTION-vN
TOOL-CONFIGURATION-vN
Record hashes for file-based artifacts where practical.
Do not alter any frozen component during the iteration batch.
If anything must change, terminate the current batch and start a new version.

11. Run ten independent executions
Create ten fresh execution contexts.
Give every execution exactly the same frozen:
• input;
• sources;
• requirements where the production agent is intended to receive them;
• production instruction;
• tool configuration.
Do not give any execution:
• another execution’s output;
• reviewer comments;
• prior failure explanations;
• proposed corrections.
Run all ten independently.
Store every output separately.
Label:
RUN-001
RUN-002
...
RUN-010

12. Verify each execution independently
Run the complete verification suite against each result.
For every requirement and run, record:
REQ_ID
RUN_ID
RESULT = SATISFIED | VIOLATED | UNDETERMINED
TEST_ID
EVIDENCE
DEFECT_ID if applicable
Do not ask the generating agent whether its own work is correct.
Run deterministic validators independently.
Run semantic evaluation independently.
Run adversarial evaluation independently where applicable.

13. Compare the ten executions
Compare outcomes requirement-by-requirement.
Identify:
• requirements satisfied by all ten;
• requirements violated by one or more;
• requirements producing inconsistent interpretations;
• outputs that vary where variation is prohibited;
• requirements that tests cannot conclusively evaluate;
• failures repeated across multiple executions;
• failures unique to individual executions.
Do not select the best execution and discard evidence from the others.
Treat variance affecting correctness as a defect requiring investigation.

14. Root-cause every defect
For each defect, determine the earliest layer at which the condition became incorrect.
Use these categories:
SOURCE_DEFECT
RESEARCH_DEFECT
REQUIREMENT_DEFECT
TEST_DEFECT
INSTRUCTION_DEFECT
INPUT_DEFECT
EXECUTION_DEFECT
TOOL_DEFECT
AUDIT_DEFECT
Determine root cause by tracing backward:
bad output
↓
was the execution compliant with the instruction?
↓
was the instruction correct relative to the requirement?
↓
was the requirement correct relative to authority?
↓
was the authority/source correct and complete?
Do not classify a defect as an instruction defect merely because changing the instruction could hide the symptom.
Correct the earliest defective layer.

15. Convert every confirmed failure into a regression test
For each confirmed defect:
1. preserve an example that reproduces it;
2. create a test that fails before the correction;
3. make the correction;
4. confirm the new test succeeds after the correction;
5. add the test permanently to the suite.
Record:
REG_ID
ORIGINAL_DEFECT_ID
REQ_ID
FAILURE_FIXTURE
DETECTION_METHOD
EXPECTED_REJECTION_OR_CORRECTION
Do not remove the regression test while the governing requirement remains applicable.

16. Revise the responsible layer
If research was wrong, redo the affected research.
If requirements were wrong, correct the requirements and every dependent artifact.
If tests were wrong, correct the tests and rerun affected validation.
If the instruction was wrong, correct the instruction.
If execution alone was wrong, preserve the instruction unless analysis establishes that additional constraint is required.
If tools were wrong, repair or replace the tool path.
Increment every changed artifact’s version.
Never modify a version in place.

17. Re-run the complete ten-execution iteration
After any material change to:
• source interpretation;
• requirement;
• production instruction;
• validator;
• tool configuration;
• input contract;
freeze the new versions and run ten new independent executions.
Do not continue the old conversations.
Use:
RUN-011 through RUN-020
or a new iteration namespace:
ITERATION-002/RUN-001 through RUN-010
Repeat:
EXECUTE
→ VERIFY
→ COMPARE
→ ROOT-CAUSE
→ CORRECT
→ ADD REGRESSION TEST
→ RE-EXECUTE

18. Continue until convergence
After every iteration calculate:
• mandatory requirement coverage;
• mandatory verification coverage;
• regression-test success;
• number of critical defects;
• number of major defects;
• number of unresolved unknowns;
• number of correctness-affecting disagreements between runs.
Do not freeze the production instruction until all of these conditions are simultaneously true:
mandatory requirement coverage = 100%
mandatory verification coverage = 100%
regression test success = 100%
critical defects = 0
major defects = 0
mandatory unresolved unknowns = 0
known correctness-affecting contradictions = 0
known correctness-affecting ambiguities = 0
unexplained correctness-affecting execution variance = 0

19. Run an unchanged confirmation iteration
After the first iteration satisfying all convergence conditions:
1. change nothing;
2. freeze exactly the same versions;
3. create ten new independent execution contexts;
4. execute the same production instruction again;
5. run the complete verification suite again.
If any new critical or major defect appears, return to root-cause analysis.
If a new requirement is discovered, return to requirement research.
If a test fails to detect an injected defect, return to test development.
Only establish the baseline after an unchanged confirmation iteration satisfies the complete acceptance criteria.

20. Freeze the production baseline
Record exact approved versions:
BASELINE_ID
INPUT_CONTRACT_VERSION
SOURCE_SET_VERSION
REQUIREMENTS_VERSION
INSTRUCTION_VERSION
TEST_SUITE_VERSION
VALIDATOR_VERSION
TOOL_CONFIGURATION_VERSION
Hash every immutable file.
No changed component retains baseline status automatically.

21. Generate the finished product
Create a fresh execution context.
Supply only the approved baseline materials required for production.
Generate the actual requested deliverable.
Record:
PRODUCT_ID
BASELINE_ID
EXECUTION_ID
OUTPUT_FILES
OUTPUT_HASHES
Do not edit the output outside the controlled workflow.
If editing is required, create a new product version.

22. Run deterministic verification on the finished product
Execute every applicable deterministic test against the actual generated artifact.
Check, where applicable:
• arithmetic;
• counts;
• schemas;
• filenames;
• file inventory;
• hashes;
• section presence;
• section ordering;
• identifiers;
• duplicate identifiers;
• references;
• links;
• dates;
• enumerations;
• tables;
• required text;
• prohibited text;
• package contents;
• structural constraints;
• formatting dimensions.
Store the actual test results.
Any failed mandatory deterministic test rejects the product.

23. Run independent semantic verification
Give a separate evaluator:
• the actual finished product;
• the requirement registry;
• relevant source evidence;
• the evaluation rubric.
For each semantic requirement, require the evaluator to identify:
REQ_ID
PRODUCT_LOCATION
SOURCE_EVIDENCE
OBSERVED_MEANING
REQUIRED_MEANING
DETERMINATION
Require SATISFIED, VIOLATED, or UNDETERMINED.
Do not accept unsupported statements such as:
looks correct
appears compliant
pass
good

24. Run adversarial verification
Attempt to disprove product correctness.
Search deliberately for:
• missing required material;
• prohibited material;
• contradictions;
• impossible logic;
• unsupported facts;
• misrepresented sources;
• wrong versions;
• broken references;
• hidden assumptions;
• partial completion;
• semantic nonsense;
• inconsistent terminology;
• unhandled exceptions;
• stale external information;
• malformed generated files;
• visually hidden content;
• export corruption;
• requirements technically mentioned but not actually satisfied.
A discovered defect returns the product to root-cause analysis.

25. Inspect the final representation
Audit the exact form that will be delivered.
If production contains transformations:
source
→ DOCX
→ PDF
→ ZIP
inspect the resulting PDF and ZIP.
Verify:
• rendered pages;
• clipping;
• missing content;
• blank pages;
• broken tables;
• misplaced graphics;
• font substitution where material;
• corrupt files;
• missing packaged files;
• unexpected files;
• wrong filenames;
• inconsistent versions.
Do not rely solely on validation of an upstream representation.

26. Reconcile process and product evidence
Before release, prove both independently:
Process correctness
Verify that:
• the approved inputs were used;
• the approved instruction was used;
• required tools ran;
• required tests ran;
• no unauthorized modification occurred.
Product correctness
Verify that:
• every mandatory product requirement is satisfied;
• every mandatory test succeeded;
• every semantic requirement has supporting evidence;
• no unresolved critical or major defect exists.
Do not infer product correctness from process correctness.
Do not infer process correctness from product correctness.

27. Apply the release gate
Assign exactly one state:
ACCEPTED
REJECTED
BLOCKED
Use:
ACCEPTED
All mandatory requirements have affirmative supporting evidence and all mandatory validators succeed.
REJECTED
At least one mandatory requirement is demonstrably violated.
BLOCKED
At least one mandatory requirement cannot be established because required evidence, authority, input, or capability is unavailable.
Do not treat absence of detected defects as proof by itself.
Acceptance requires affirmative verification evidence for every mandatory requirement.

28. Verify artifact identity before release
Calculate the cryptographic hash of every artifact that completed final verification.
Immediately before delivery, calculate the hash again.
Require:
RELEASE_HASH = AUDITED_HASH
If any hash differs:
1. stop release;
2. identify the modification;
3. create a new product version;
4. rerun every validation affected by the modification;
5. perform the release gate again.
Never release a modified artifact under an earlier audit.

30. Preserve failures permanently
Maintain a defect registry.
For every defect record:
DEFECT_ID
DATE
ITERATION
PRODUCT_VERSION
REQUIREMENT
OBSERVED_FAILURE
ROOT_CAUSE

Before approving any later baseline, execute all still-applicable regression tests.
A previously solved defect that reappears is a regression and prevents release.

Mandatory operating rules
1. Do not begin production before requirements and acceptance tests exist.
2. Do not invent missing facts.
3. Do not silently resolve authoritative conflicts.
4. Do not allow the generator to be its sole validator.
5. Use deterministic verification whenever the property is deterministically testable.
6. Require affirmative evidence for every mandatory requirement.
7. Treat mandatory unknowns as BLOCKED.
8. Root-cause every material failure before changing anything.
9. Correct the earliest defective layer rather than merely patching the final output.
10. Convert every confirmed defect into a permanent regression test.
11. Re-run independent executions after every material upstream change.
12. Do not allow independent iterations to see one another’s outputs.
13. Do not freeze a baseline merely because ten runs completed.
14. Require an unchanged confirmation iteration.
15. Validate the actual finished artifact, not merely its source representation.
16. Invalidate affected downstream verification whenever an upstream artifact changes materially.
17. Do not release any product containing an unresolved critical or major defect.
18. Do not release a product whose mandatory requirement cannot be verified.
19. Do not release bytes different from the bytes that were audited.
20. Preserve enough evidence to reproduce every acceptance decision.
